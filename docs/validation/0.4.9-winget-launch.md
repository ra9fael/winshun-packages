# 0.4.9 local validation — WinGet launch failure (error 87)

## Symptom

The scan reported:

```text
winget --version could not be launched: The parameter is incorrect.
```

while `winget --version` worked in a normal shell. The plugin process was a
normal-user process; the failure was inside the plugin's own child launch.

## Root cause

0.4.8 started passing a custom environment block (to override `USERPROFILE`)
but never set `CREATE_UNICODE_ENVIRONMENT`. Windows therefore parsed the UTF-16
block as ANSI and `CreateProcessW` failed with `ERROR_INVALID_PARAMETER` (87).
Reproduced outside the plugin:

```text
env override: launched=0 err=87
```

The same block, passed with `CREATE_UNICODE_ENVIRONMENT`, launched normally, so
the block contents (including the `=C:` drive entries and sorting) were never the
problem.

## Fixes

- `CREATE_UNICODE_ENVIRONMENT` is now set whenever a block is supplied.
- The block is now complete: inherited variables plus the overrides, sorted as
  Windows expects. 0.4.8 passed only the override entry, which dropped `PATH`,
  `SystemRoot` and everything else.
- `GetUserProfileDirectoryW(token, nullptr, &size)` does not exist as a size
  query (it returns FALSE with size 0), so the profile override silently never
  applied. It now uses a real buffer and trims the terminator.
- A launch failure is recorded to `<plugin data>\launch-failures.log` with the
  path used, the Win32 error and the profile variables, because a one-line
  status cannot explain this class of failure. A crash while writing that record
  (long PATH → constructing a string from the required length) was fixed by
  truncating instead.

## Verification

- `packages_process_tests`: 27 checks, 0 failures, including new cases for
  "environment overrides keep the rest of the block" and "a launch failure is
  recorded for diagnosis".
- `packages_probe_winget` (development-only tool) reports
  `launched=1 exit=0 output=v1.29.380`.
- No package was installed, upgraded or removed for this validation.
