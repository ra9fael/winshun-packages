# 0.4.10 local validation — Discover search cache

## What was wrong

A search ran `winget search` plus `scoop search` every time, and the answer lived
only in memory: typing the same word again, or switching tabs and back, cost the
same two processes. `cache.json` covered the inventory and updates only.

## What changed

- New pure module `src/core/search_cache.cpp`:
  - `normalizeQuery` trims, collapses whitespace and lower-cases (both backends
    match case-insensitively, so `Vim` and `"  vim "` are one entry).
  - `fileStem` is FNV-1a over the normalised query, so a query containing path
    characters cannot escape the cache folder.
  - The entry itself is written with `cache::serialize`, so there is one tested
    serialiser for both inventory and search snapshots.
  - `worthWriting` refuses entries without a timestamp or from a scan where both
    backends failed; an empty result from a backend that ran is kept.
- `Controller::startSearchWorker` now tries `applyCachedSearch` **before** the
  probe check, so a cached answer needs no backend at all.
- The cache is cleared when any task finishes (a mutation changes what a search
  should return) and by "清除缓存".
- The settings popup's cache summary reports the number of cached queries.
- `platform::ensureDirectory` / `platform::pruneOldFiles` provide the folder and
  the 60-entry cap (oldest file first).

## Verification (development harness, real backends)

```text
run 1  search "vim"   -> writes 84322251696c124d.json (17 KB)
run 2  same query     -> file untouched, 1.7 s to results, no backend search
TTL    observedAt aged 3 h -> entry refreshed by a real search
```

Core tests: 303 checks, 0 failures (37 new checks covering normalisation, file
stem stability and safety, path building, round trip, and the "never cache a
failed scan" rule).

Screenshot `search-cached.png` shows 21 cached rows with the scan timestamp.
