# Packages：可编辑设置与搜索动作改进方案

[English](sdk-upgrade-plan.en.md)

## 改动原因

宿主能将设置传入 Controller，但软件包窗口的设置弹层只是只读摘要。用户需要离开工作窗口，才能修改扫描策略、信息获取和缓存期限。

搜索结果目前只有打开窗口一行。插件已通过独立命令实现普通打开、仅看缓存和强制刷新，把这些能力配置到结果动作菜单即可提高可发现性。

## 界面分工

现有七项设置数量不多，全部保留在宿主卡片：语言、显示 observed-only 项、缓存刷新间隔、选中后获取信息、打开时扫描策略、插件启动时扫描、详细诊断。

窗口设置弹层改为可编辑，显示同一组设置，并保留缓存和探针摘要、显式缓存维护操作。

| 搜索结果动作 | 行为 |
|---|---|
| 打开 | 遵循保存的打开时扫描策略 |
| 仅打开缓存 | 不查询后端 |
| 打开并刷新 | 忽略缓存新鲜度，重新查询 |
| 设置 | 打开配置，不触发额外扫描 |

独立关键词入口不再保留，这些能力集中在 `packages` 结果动作上。安装、卸载和升级继续进入现有身份与计划审阅流程。

## 实现方案

1. 更新 SDK，增加 Controller 向协议层报告配置修改的通道。
2. 将摘要字段换成选择、开关和数值控件，逐项通过 `updateSettings()` 提交修改。
3. 宿主下发只应用不回发；修改单项保留其他六项。七项偏好全部由宿主持久化，缓存继续存放在插件数据目录。
4. 为刷新间隔增加单位和合理范围前，确认当前合法值与特殊值语义。如果 0 有受支持的意义，就提供独立选项，不能被数值规范化悄悄改掉。
5. 将结果动作映射到现有 `OpenMode`，保留搜索词向窗口传递的路径。
6. 接入 `settingsWindow` 和 `showSettings()`，通过无扫描打开方式显示现有设置内容；lazy 插件保留搜索设置动作作为冷启动入口。
7. 保留“插件进程启动时扫描”的含义。设置动作本身不新增扫描；独立配置的进程启动扫描仍按原语义发生。

## 验收标准

- 窗口修改任一设置都同步宿主，重启后恢复。
- 修改单项不覆盖其他项。
- 仅看缓存和设置动作不发起后端查询；独立启用的进程启动扫描按其明确语义验证。
- 强制刷新绕过新鲜度，普通打开遵循策略。
- 搜索词仍进入现有发现流程；修改设置不自动安装、卸载或升级。
- 相关 Controller、协议和假数据界面验证通过。
